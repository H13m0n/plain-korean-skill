# 패턴과 예외

아래 예시는 모두 새로 쓴 가상 문장이다. 단어보다 문장의 기능을 보고 적용한다. 전체 예시와 유지 사례는 [examples.jsonl](examples.jsonl)에 있다.

| 살필 전개 | 편집 기준 |
|---|---|
| 제안 설명 뒤마다 미정 상태 반복 | 제목·머리말에서 범위를 설명하고 중복을 삭제한다. 일정과 결정을 묻는 글에는 상태를 남긴다. |
| 요청하지 않은 비교로 역할 설명 | 해당 대상의 주체·동작을 쓴다. 비교 질문에는 차이를 답한다. |
| 소개·설치 안내에서 “~하지 않습니다”, “필수가 아닙니다” 반복 | 사용 방법과 준비물을 직접 쓴다. 불필요한 해명은 덜어내고 문장 관계와 말투도 다듬는다. |
| 검색·확인 과정이 본문을 차지 | 독자에게 필요한 결과와 근거를 쓴다. 조사 실패가 판단에 중요하면 남긴다. |
| 추상적인 관리 동사 | 기록할 값, 검사할 위치, 가져와 쓸 절차를 쓴다. 정확한 기술 행위를 뜻하면 유지한다. |
| 주장 뒤에 관성적인 평가 필요 문장 | 주장의 주체를 밝힌다. 실제 평가 계획과 불확실성은 필요한 위치에 남긴다. |
| 개요에서 날짜·버전·식별자 나열 | 호환성·재현·일정에 필요한 값만 본문에 둔다. 출처 기록의 정밀 정보는 보존한다. |
| “뿐 아니라 함께”로 항목 추가 | 비교할 항목을 직접 나열한다. 실제 추가 관계를 강조할 필요가 있으면 유지한다. |
| 명사끼리 이어 붙인 표현 | 누가 무엇을 설명하는지 연결한다. 고유 명칭은 유지한다. |
| 가정한 테스트를 관찰 사례로 소개 | 가정과 관찰을 구별한다. 대표성이 확인된 사례는 그 범위대로 쓴다. |
| 같은 대상의 이름을 계속 변경 | 이름을 통일한다. 서로 다른 대상의 차이는 유지한다. |
| 설명 뒤에 붙인 반복 결론 | 새 정보가 없으면 삭제한다. 독립해서 읽는 요약은 남길 수 있다. |
| 짧게 끊긴 동작 설명 | 원인·조건·결과를 연결한다. 독자가 따라 할 단계는 나눌 수 있다. |

예를 들어 “캐시는 조회를 줄인다. 이 저장 계층은 결과를 보관한다. 해당 보관 장치는 다음 요청에 응답한다.”는 같은 대상을 다른 이름으로 부른다. “캐시는 결과를 보관해 다음 조회에 사용한다.”로 연결할 수 있다.

반면 “연결이 끊겨도 작업은 계속 실행된다”는 장애 조건을 설명한다. 부정·조건 표현이 있다는 이유로 삭제하지 않는다. “삭제한 자료는 복구할 수 없다”도 실제 제한이면 그대로 남긴다.

새 기준은 수정 예와 함께 **유지할 문맥**을 포함해야 한다. 글의 목적이 다른데 한 가지 문체를 강요하지 않는지 확인한다.

## 무엇을 안 하는지 늘어놓는 소개글

소개글에서 독자가 묻지도 않은 제한·부정·면책을 나열하면 글이 딱딱해진다. “않습니다”를 최대한 덜 쓰고, 독자에게 필요한 내용을 문장부터 다시 쓴다.

| 살필 문장 | 수정 방향과 예 |
|---|---|
| “단어를 일괄 금지하거나 AI 작성 여부를 판정하지 않습니다.” | 소개에는 어떻게 다듬는지 쓴다. “글의 뜻과 말투를 살려 읽기 편하게 다듬습니다.” 평가 방법을 묻는 문맥에서는 실제 기준을 답한다. |
| “본문 지침과 예시는 특정 운영체제나 서비스에 의존하지 않습니다.” | 설치 방법을 안내한다. “스킬 폴더를 사용하는 도구의 스킬 디렉터리에 복사하세요.” 지원 환경을 묻는 문맥에서는 확인한 환경을 적는다. |
| “다른 윤문 스킬과 API 키는 필수가 아닙니다.” | 해당 기능의 준비물을 쓴다. “글 다듬기는 설치한 스킬 지침으로 동작합니다.” 기여 도우미처럼 추가 도구가 필요한 기능은 별도로 안내한다. |
| “스킬 폴더가 배포 원본이며 생성된 복제본을 따로 관리하지 않습니다.” | 실제 관리 절차를 쓴다. “스킬을 고칠 때는 해당 폴더를 수정하고, 배포할 때 이 폴더를 복사합니다.” |
| “Python 표준 라이브러리만 사용하고 테스트는 실제 이슈를 만들지 않습니다.” | 실행 방식과 검사 대상을 쓴다. “Python 표준 라이브러리로 검사합니다. GitHub 호출은 모의 응답으로 대체합니다.” |

문장의 용도에 맞춰 삭제·재작성·재배치를 고른다. “특정 서비스 의존성이 없습니다”처럼 부정의 뜻을 다른 어미로 옮기면 같은 설명이 남는다. 실제 제한을 묻는 질문과 데이터 손실·금지 사항을 알리는 문맥에서는 필요한 부정을 유지한다.

## 읽는 사람에게 자연스럽게 말하기

문장을 줄인 뒤에도 사람이 건네는 말처럼 읽히는지 살핀다. 업무 메일에서는 진행 상황과 부탁을 연결하고, 기술 안내에서는 사용자가 겪는 상황과 할 일을 연결한다.

**업무 메일**

- 수정 전: “초안 작성이 완료된 상태이며, 검토 의견 반영은 아직 진행되지 않았습니다. 확인 후 의견을 전달해 주시면 반영 작업을 진행하겠습니다.”
- 수정 후: “초안을 써뒀습니다. 읽어보시고 의견을 주시면 반영하겠습니다.”

**기술 안내**

- 수정 전: “연결이 끊긴 경우에도 처리 중인 작업은 취소되지 않습니다. 작업 완료 여부에 대한 확인은 재연결 이후에 진행할 수 있습니다.”
- 수정 후: “연결이 끊겨도 작업은 계속됩니다. 다시 연결한 뒤 완료 여부를 확인하세요.”

두 예시는 사실과 조건을 유지하면서 명사 중심 표현을 풀고, 독자에게 말을 건네는 어휘와 문장 순서를 고른다. 공문이나 규격 문서에서는 해당 문서의 격식과 정확한 용어에 맞춰 쓴다.

## 소개글에 필요한 내용 고르기

사용하는 사람이 당장 할 일을 기준으로 내용을 고른다. 사용 예·설치·호출·설정 방법을 소개글에 두고, 개발 과정과 구조 선택은 설계 문서, 검사 명령은 기여 문서, 라이선스 전문은 LICENSE 파일에 둔다. 사용자가 요청한 출처나 비교 설명은 해당 문맥에 맞게 제공한다.
